# Maharashtra Citizen Certificate Portal

A citizen-facing portal prototype for applying for revenue certificates. Citizens browse five certificate services, fill in an application, upload documents, pay the fee, track the application, and download the issued PDF certificate. Logged-in citizens also get a My Account page that lists their applications, certificates and payment history.

> **Prototype note (for developers):** login, payment and officer approval are simulated by the system. The citizen-facing screens deliberately do not label them as simulated, because the portal is presented as a finished product. Each generated PDF carries a `SAMPLE` watermark (one large mark plus small repeated marks across the page) and the footer line `Sample generated by prototype system – not for official use.` so it cannot pass as a real certificate. Keep that marking. The page footer reads "Prototype developed for evaluation by the Government of Maharashtra".

This is the baseline "legacy" codebase for the developer training sessions. See [prd.md](prd.md) for the requirements and [PLAN.md](PLAN.md) for the build plan.

## Tech stack

| Layer | Technology |
| --- | --- |
| Frontend | Static HTML, Tailwind CSS (Play CDN), vanilla JavaScript |
| Backend | Python 3.12, FastAPI |
| Database | SQLite via SQLAlchemy |
| PDF | ReportLab (includes its built-in QR code widget) |
| Container | Docker / Docker Compose |

FastAPI serves the REST API under `/api` and the static frontend from `/`. The whole app is one process in one container.

## Quick start

```bash
./script.sh                              # build, start, wait until healthy, open the browser
./script.sh stop | restart | logs | status
PORT=8090 APPROVAL_DELAY_SECONDS=20 ./script.sh   # other port, faster approval
```

On Windows, run it from Git Bash. The script checks that Docker is running and that the port is free.

## Run with Docker (recommended)

```bash
docker compose up --build
```

Then open http://localhost:8000. If port 8000 is already in use, run `PORT=8090 docker compose up --build` and open http://localhost:8090.

Data is stored in the named volume `portal_data`, mounted at `/data`. It holds the SQLite database, uploaded documents and generated PDFs, so they survive container restarts:

```bash
docker compose restart      # data is kept
docker compose down         # data is kept (the volume remains)
docker compose down -v      # deletes the volume and ALL data
```

To use plain Docker instead of Compose:

```bash
docker build -t maha-portal .
docker run -p 8000:8000 -v maha_portal_data:/data maha-portal
```

## Run locally (without Docker)

Requires Python 3.12.

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate    macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
cd backend
uvicorn app.main:app --reload
```

By default, data is written to `./data` in the project root.

## Configuration

All settings are environment variables.

| Variable | Default | Description |
| --- | --- | --- |
| `DATA_DIR` | `./data` (`/data` in Docker) | Folder for the SQLite DB, uploads and certificates |
| `APPROVAL_DELAY_SECONDS` | `90` | Seconds after submission before the simulated approval |
| `APPROVAL_POLL_SECONDS` | `10` | How often the approval worker checks the database |
| `APPROVAL_WORKER_ENABLED` | `true` | Turns the background approval worker on or off |
| `MAX_UPLOAD_MB` | `5` | Maximum size of each uploaded document |
| `PUBLIC_BASE_URL` | `http://localhost:8000` | Base URL printed in the certificate QR code |

For a faster presentation, set `APPROVAL_DELAY_SECONDS=20`.

## API

Interactive API docs: http://localhost:8000/docs

| Method | Endpoint | Purpose |
| --- | --- | --- |
| GET | `/api/certificates` | List the certificate services |
| GET | `/api/certificates/{id}` | Get one certificate service |
| GET | `/api/districts` | List Maharashtra districts (for the form) |
| POST | `/api/applications` | Submit an application with the logged-in `account_mobile` and the successful payment details |
| POST | `/api/applications/{reference}/documents` | Upload one document (multipart: `doc_type`, `file`) |
| GET | `/api/applications/{reference}` | Get application details |
| GET | `/api/applications/{reference}/status` | Get the current status and history |
| GET | `/api/applications/{reference}/certificate` | Download the PDF (returns 409 until generated) |
| POST | `/api/payments/failed` | Record a failed or cancelled payment attempt |
| GET | `/api/citizens/{mobile}/applications` | A citizen's applications and issued certificates |
| GET | `/api/citizens/{mobile}/payments` | A citizen's payment history (success and failed) |
| GET | `/api/citizens/{mobile}/eligibility/{certificate_type}` | Whether the citizen can apply for this certificate now |
| GET | `/api/health` | Health check |

The PRD names the upload path `{id}`. This implementation uses the application reference number, to match the other endpoints.

Login and registration have no backend APIs; they are simulated in the browser. Payment processing is also simulated in the browser, but the results are stored: successful payments with the application, and failed attempts through `/api/payments/failed`. This goes beyond PRD section 4.6, so that My Account can show payment history.

Citizens are identified by the mobile number they log in with. The `/api/citizens/{mobile}/...` endpoints have no authentication, because the prototype has none (PRD section 4.2). Add real authentication before using them with real data.

Validation errors return `422` with `{"detail": {"message": ..., "fields": {field: message}}}`, using plain-language messages.

## Certificate validity and re-application rules

The rules are set per certificate in `catalog.py` (`validity_months`, `reapply`) and applied in `services/validity.py`.

| Certificate | Validity | When a citizen can apply again |
| --- | --- | --- |
| Income | 1 year from issue | Only after the current certificate expires |
| Caste | Permanent | Never: one per citizen account |
| Domicile | Permanent | Never: one per citizen account |
| Residence | 1 year from issue | Only after the current certificate expires |
| Non-Creamy Layer | 1 year from issue | Any time, any number of times |

- Rules are checked per citizen account (the login mobile number).
- A pending application also blocks a new one for Income, Residence, Caste and Domicile.
- The apply page calls the eligibility endpoint before the form, so a citizen is never charged for an application that will be refused.
- `POST /api/applications` checks the same rules again and returns `409` if they are not met.
- The validity date is stored in `certificates.valid_until`; `NULL` means permanent. It is printed on the PDF and shown in My Account.
- Databases created before this change are upgraded: existing Income, Residence and NCL certificates get one year from their issue date.

## How the approval workflow works

1. After a successful payment, the browser submits the application with the payment details. The backend saves it with status `SUBMITTED` and returns a reference number such as `MH-APP-20261030-7K2Q9D`.
2. The browser then uploads each selected document to `/documents`. Files are saved under random UUID names. They are checked by extension, size and file signature.
3. A background task in the FastAPI process checks the database every `APPROVAL_POLL_SECONDS`. When an application has been `SUBMITTED` for longer than `APPROVAL_DELAY_SECONDS`, the task:
   - moves it to `APPROVED` and records a (fictional) approving officer;
   - generates the PDF certificate;
   - moves it to `CERTIFICATE_GENERATED`.
4. Every transition is written to `application_status_history`.

The workflow is driven by the database, so it is not affected by browser refreshes. It also resumes after a server or container restart.

The frontend polls for status changes and shows toast notifications. It polls on the tracking page and also on every page for applications submitted from that browser.

## Presentation walkthrough

1. Open http://localhost:8000 and browse the certificate services.
2. Click **Register**, create an account (any valid mobile number), and you are logged in.
3. Choose **Income Certificate** and click **Apply Now**.
4. Fill in the form and click **Save & Continue**.
5. Upload a PDF, JPG or PNG for each required document.
6. Review the details, accept the declaration and proceed to payment.
7. Choose UPI and enter any ID such as `ramesh@upi`. Click **Pay**. To show a failed payment, click **Cancel Payment** instead, then **Retry Payment**.
8. The receipt shows the transaction ID and the application number with a copy button. Click **Track Application**. The status shows `SUBMITTED`.
9. After about 1–2 minutes, a notification appears and the status becomes `CERTIFICATE GENERATED`.
10. Click **Download Certificate (PDF)**. Open **My Account** to see all applications, certificates and the payment history, including the failed attempt.

## Tests

```bash
cd backend
pytest
```

The tests use a temporary data folder and disable the background worker. They run the approval cycle directly.

## Out of scope

This version has no real authentication, payment gateway, officer dashboard, digital signatures, OCR, external government integrations, or email/SMS notifications. See section 10 of the PRD.
